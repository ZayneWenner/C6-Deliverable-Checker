# 交付物体检站 · Deliverable Checker

一个**零依赖、纯前端**的交付物自动体检工具。用于在提交作业 / 项目材料之前，提前发现「缺文件」和「命名不合规」两类致命错误——这两类错误在人工检查时最容易被漏掉，却会直接导致提交被平台判为不合格。

> 在线使用：见仓库右侧 About 中的 Pages 链接，或直接打开 `index.html`（无需服务器）。

## 它解决什么问题

在线课程 / 平台作业的提交校验，通常按「交付物模式」匹配文件名，例如：

```
*app链接*,*demo*,*repo链接*,*AI日志*
```

其中 `*X*` 表示**文件名必须包含 X**（忽略大小写），不带 `*` 表示**文件名必须完全相等**。

这套规则看起来简单，实际非常容易踩坑：

| 你的文件名 | 模式 | 结果 | 原因 |
| --- | --- | --- | --- |
| `AI日志.md` | `*AI日志*` | ✅ 通过 | 四字连续 |
| `AI协作日志.md` | `*AI日志*` | ❌ 不通过 | 中间多了「协作」 |
| `AI_LOG.md` | `*AI日志*` | ❌ 不通过 | 英文名不匹配中文模式 |
| `AI 日志.md` | `*AI日志*` | ❌ 不通过 | 中间有空格 |

这类错误往往要等到提交后回看结果才发现，而那时已经消耗了一次提交机会。本工具把这道检查提前到本地、离线、即时完成。

## 核心功能

1. **挑战选择**：内置 20 个挑战的交付物模式，选中即加载对应规则。
2. **文件纳入**：拖拽整个文件夹、多选文件，或直接粘贴文件名列表（不方便上传时用）。
3. **自动体检**：逐项匹配交付物，输出命中 / 缺失 / 未归因文件三张清单。
4. **命名体检**：识别常见的命名陷阱（中文不连续、英文别名、空格、0 字节文件），给出具体修改建议。
5. **报告导出**：一键导出 Markdown / CSV 体检报告，可直接贴进提交说明。
6. **AI 归因（可选，BYOK）**：把你的文件清单交给大模型，让它解释「每个文件为什么不合格、怎么改」。**需要自填 API Key**，见下文。

## AI 部分的设计与边界（重要）

AI 是**可选增强**，不是必需品：即使完全不配置 Key，规则引擎也能完成全部核心检查（第 1–5 项）。这样设计的原因有两个：

- **平台要求前端不得硬编码 Key**。本项目没有任何后端，也不做请求中转；Key 只保存在你自己浏览器的 localStorage，请求由浏览器直接发往你选择的服务商。因此它采用 **BYOK（Bring Your Own Key）** 模式。
- **降低评判风险**：如果 AI 不可用就整个功能不可用，那 AI 就成了摆设。所以规则引擎是主线，AI 是叠加的解释层。

支持两种协议：

| 预设 | Base URL | 默认模型 |
| --- | --- | --- |
| OpenAI 兼容 | `https://api.openai.com/v1`（任何 OpenAI 兼容网关都行） | `gpt-4o-mini` |
| Anthropic | `https://api.anthropic.com` | `claude-3-5-haiku-latest` |

Key 存储位置：localStorage 键 `dc_ai_cfg_v1`。点「清除」即可删除；不会上传到任何地方（本项目没有服务器）。不过请注意：在公用电脑上使用后应主动清除。

## 本地运行

```bash
# 方式一：直接双击打开
index.html

# 方式二：起一个静态服务器（推荐，避免个别浏览器的 file:// 限制）
python -m http.server 8080
# 然后访问 http://localhost:8080
```

无构建步骤、无 npm install、无 CDN 依赖。

## 测试

规则引擎是纯函数，可脱离浏览器直接测试：

```bash
node test/engine.test.js
```

当前 **32 项断言全部通过**，覆盖：模式解析、平台匹配语义、C6 完整文件集、缺项判定、命名陷阱识别、0 字节文件、报告导出。用例直接取自真实踩过的坑（`AI协作日志.md`、`AI_LOG.md`）。

## 目录结构

```
.
├── index.html              # 单页应用入口
├── assets/
│   ├── styles.css          # 深色主题，含 640px 移动端断点
│   ├── data.js             # 20 个挑战的交付物模式（window.CHALLENGE_DATA）
│   ├── engine.js           # 规则引擎（纯函数，双导出）
│   ├── ai.js               # AI 归因（BYOK，双协议）
│   └── app.js              # 交互层：拖拽、渲染、导出
├── test/engine.test.js     # 32 项断言
├── demo/                   # 真实运行截图
└── ATTRIBUTION.md          # 拿来说明：哪些是原创、哪些是借用的
```

`engine.js` 同时支持浏览器（`window.Engine`）与 Node（`module.exports`），因此测试无需模拟浏览器环境。

## 技术选型说明

选用**原生 HTML + CSS + JS，不引入框架**，是一个刻意的决定：

- 这是一个单页、状态极简（一份文件清单 + 一个挑战）的工具，React 的组件化收益在这个规模上体现不出来，反而带来构建链和部署复杂度。
- 零依赖意味着**十年后打开仍然能跑**，不会因为某个依赖停止维护而失效。
- 交付要求「部署后能访问」，静态文件托管即可满足，无需 Node 运行时。

代价是：如果后续要加多步骤工作流、状态持久化、协作编辑，原生 DOM 操作会变得笨重——那时再引入框架是合理的。
